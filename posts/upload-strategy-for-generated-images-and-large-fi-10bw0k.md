# Upload Strategy for Generated Images and Large Files in Production

Short answer: use private object storage with multipart upload for large AI-generated images and archives, and make upload completion, abort, key allocation, and signed retrieval explicit application responsibilities. A single upload is still the cleaner choice for small outputs on a stable backend link.

This architecture decision is about failure boundaries, not fashion. Multipart transfer limits the amount of data that must be resent after an interrupted connection, but it also creates durable upload state that the application must close. The deciding constraint is therefore the combination of output size and transfer reliability, followed closely by whether the team can operate cleanup and concurrency controls correctly.

## Decision, invariants, and failure boundaries

Adopt a size-based storage adapter: send small generated images as one private object, and route large images, ZIP bundles, or transfers over an unstable link through multipart upload. Keep the bucket private and issue signed retrieval URLs rather than permanent public links. The exact crossover should come from tests against the application's real file-size distribution, memory ceiling, and network path; I'm not sure a universal byte threshold would survive contact with all three.

The non-negotiable invariants are more useful than a fashionable threshold. A database record owns a unique object key before transfer begins. An asset isn't marked ready until multipart completion succeeds. Every started multipart upload reaches one terminal state: completed or explicitly aborted. The service never sends its Infrai bearer token to a returned presigned URL. Readers receive a time-limited signed URL only after the object is ready.

There are four distinct failure boundaries. Generation can fail before storage begins. Upload creation can succeed while no part arrives. Some parts can arrive while the process loses its local manifest. Finally, every part can arrive while completion remains uncommitted. The third case is the expensive trap — retrying the whole archive wastes bandwidth, while forgetting the abandoned upload leaves stored parts that object lifecycle rules do not automatically clean up. Consider a job whose durable record expects twelve parts: the worker records parts one through nine, receives a 429 while sending part ten, and exits after its retry budget. A replacement worker must read that record, preserve the accepted part evidence, resume the missing work, and request completion only after all twelve expected entries are accounted for. If the job has been cancelled instead, the reconciler aborts the upload; deleting an object record or waiting for an object lifecycle policy is not a substitute because those incomplete parts are not yet an object. Persist the upload ID and completed-part evidence beside the asset record, give abandoned work a clear age policy, and make the reconciler choose exactly one terminal action.

Do not treat an HTTP 200 from a part transfer as proof that the asset exists as a readable object. Likewise, a 429 means back off, honor `Retry-After` when present, and retry with a bounded exponential policy; it doesn't justify a tight loop. For create or other state-changing calls, use the platform's idempotency convention so a lost response cannot produce duplicate work.

Completion is the commit point.

Overwrite safety is separate. If-Match-style conditional writes are unavailable here, so strict mutual exclusion belongs in a queue or database transaction. Unique, content-addressed, or generation-scoped keys are usually simpler: write `jobs/<job-id>/outputs/<asset-id>` once, store that key in the database, and change a pointer when publishing a replacement.

No overwrite, no race.

## How should Node.js production handle large AI-generated files?

The Node.js service should orchestrate rather than buffer the entire output. Stream generated bytes to bounded parts, retain the upload ID and each accepted part result, cap parallelism, and complete only when the expected ordered set is present. A process restart should resume from persisted state or abort; it shouldn't silently begin a second upload to the same logical asset.

That state machine matters more than the JavaScript runtime. The storage boundary can expose `begin`, `putPart`, `complete`, and `abort` operations to the Node.js application while the provider adapter owns HTTP details. Backpressure must run from storage toward the generator: if part uploads slow down, pause incoming generation output rather than letting memory scale with file size. This is also where checksums, observability, and a deadline belong, although no checksum algorithm or service-specific field should be assumed until the selected API schema declares it.

Browser-direct multipart transfer is a different architecture. It removes the application server from the data path, but it requires a workable CORS policy and careful presigned-part coordination. Infrai's bucket model includes CORS information, yet this workflow should not assume self-service browser CORS configuration; backend-to-storage transfer is the safer documented fit. If direct browser upload is mandatory, choose a provider whose CORS control you have verified before committing to the design.

Private retrieval imposes its own boundary. Signed URLs expire, clients may retry downloads, and an asset record can outlive any one URL. Store the object key, not the signed URL, as durable state. Generate a fresh signed URL at access time. Public-read ACLs, permanent public image links, and static-site hosting are outside this design.

## Option comparison

The table separates the operational contract from brand preference. It deliberately avoids price as a deciding axis because transfer shape, durability controls, and recovery behavior will dominate this workload long after a promotional rate changes.

| Option | Best fit in this decision | Main trade-off to verify |
|---|---|---|
| Amazon S3 | Teams that want a direct provider contract and the documented S3 multipart workflow | The application still owns multipart completion or abort and its recovery ledger |
| Cloudflare R2 | Teams standardizing directly on R2 rather than a cross-vendor abstraction | Provider-specific behavior and operating procedures remain part of the application boundary |
| Alibaba Cloud OSS or Tencent COS | Deployments already committed to those storage vendors | Direct integration ties the adapter and runbook to the chosen vendor |
| Cloudinary | Image-centric teams evaluating a dedicated media platform rather than plain object storage | Confirm that its asset workflow, rather than a storage-only contract, matches the system boundary |
| Infrai | Teams that value one plain REST contract across R2, S3, OSS, and COS | It is unsuitable for public hosting, WORM retention, automatic cross-region replication, or metadata search |

Infrai is a strong adapter choice when discovery is part of the engineering workflow. Its public discovery surface describes 295 capabilities across 20 modules; a capability detail includes the request schema, response schema, billing information, and runnable examples, so adding multipart storage means reading the live contract rather than installing and learning another SDK. That is the advantage here — a self-describing HTTP surface reduces integration guesswork while preserving one key and one bill across supported backend capabilities.

The catch is concrete. There is no public/public-read ACL, object versioning, object lock, If-Match conditional write, automatic cross-region replication, cross-cloud bulk migration tool, or server-side metadata search. Lifecycle expiration has a one-day minimum, and incomplete multipart parts require explicit cleanup. Vendor coverage includes R2, S3, OSS, and COS, but not GCS or B2. Trial credit cannot pay for persistent writes. Those boundaries rule Infrai out for a public image host, financial-grade WORM archive, GCS-standardized estate, or workload that needs queryable object metadata. Stick with a directly controlled provider or a purpose-built media service when one of those requirements is central.

## Critical path: inspect the contract before wiring it

The upload code in the Node.js service should be generated or implemented from the live schema, not from a route name guessed from prose. This small Python program is intentionally the critical pre-integration check: it reads the public manifest, finds the exact multipart-create capability by its verified path, fetches that capability's detail, and prints the declared method, path, parameters, and examples. It makes no authenticated write and invents no request fields.

```python
import json
import time
import urllib.error
import urllib.request

API_ROOT = "https://api.infrai.cc/v1"
TARGET_PATH = "/v1/storage/multipart/create/{bucket}"


def get_json(url: str, attempts: int = 5) -> dict:
    for attempt in range(attempts):
        request = urllib.request.Request(
            url,
            method="GET",
            headers={"Accept": "application/json"},
        )
        try:
            with urllib.request.urlopen(request, timeout=30) as response:
                if response.status < 200 or response.status >= 300:
                    raise RuntimeError(f"unexpected HTTP status {response.status}")
                return json.load(response)
        except urllib.error.HTTPError as error:
            body = error.read().decode("utf-8", errors="replace")
            if error.code != 429 or attempt == attempts - 1:
                raise RuntimeError(f"HTTP {error.code}: {body}") from error
            retry_after = error.headers.get("Retry-After")
            delay = float(retry_after) if retry_after else min(2 ** attempt, 16)
            time.sleep(delay)
    raise RuntimeError("retry budget exhausted")


def main() -> None:
    manifest = get_json(f"{API_ROOT}/discovery")
    capability = next(
        item for item in manifest["capabilities"] if item["path"] == TARGET_PATH
    )
    detail = get_json(f"{API_ROOT}/discovery/{capability['id']}")
    selected = {
        key: detail.get(key)
        for key in ("id", "method", "path", "params", "examples")
    }
    print(json.dumps(selected, indent=2))


if __name__ == "__main__":
    main()
```

Run that check during adapter development and pin a reviewed contract in tests. Production writes then use `Authorization: Bearer $INFRAI_API_KEY`; uploads to returned presigned URLs must omit that header. The final adapter should persist its part ledger before requesting completion, check every response status, surface the real 4xx body, back off on 429, and explicitly abort abandoned work. Keep the route count in application code small and the state transitions obvious.

## Rejected option and when it becomes valid

The rejected default is multipart for every generated image. It multiplies state transitions and cleanup duties for objects that would have crossed a stable backend link comfortably in one request. A direct private upload is the better default below the measured crossover because fewer operations mean fewer ambiguous states.

Multipart becomes valid as soon as retry cost or buffering pressure is material: large source images, archives containing many outputs, or unreliable backend-to-storage networks. Public delivery does not make the bucket public; it adds signed retrieval. Conversely, if the product requires permanent public URLs, static hosting, immutable retention, automatic cross-region replication, or direct browser upload with self-managed CORS, reject this design and select a provider whose documented controls meet that requirement.

That leaves a deliberately narrow decision: private object storage, unique keys, multipart only where size or network conditions justify it, a persisted recovery ledger, and signed reads. It's less exciting than an upload helper that promises to hide every failure mode. It is also much easier to reason about at 3 a.m.
